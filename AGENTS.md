# AGENTS.md

## Project

Personal "about me" page. Vue 3 single-page app (no router) living entirely in `frontend/`, built with Vite (`rolldown-vite`) + TypeScript, deployed to GitHub Pages. No backend.

## Commands (run from `frontend/`)

- `npm run dev` — dev server
- `npm run build` — runs `type-check` and `build-only` in parallel (`run-p`); this is the full verify step
- `npm run type-check` — `vue-tsc --build`
- `npm run lint` — oxlint then eslint, **both with `--fix`** (will modify files)
- `npm run format` — `prettier --write src/`
- `npm run generate:llms` — regenerates `public/llms/*.md` + `public/llms.txt` (also run automatically by `predev`/`prebuild`)

Verify order: `lint` → `build`. There is no test suite (`src/**/__tests__/*` is excluded from tsconfig).

- `npm run eval:retrieval` — systematic retrieval evaluation (`scripts/eval-retrieval.mjs`): loads the real registry + retriever in Node (TS transpiled with the local `typescript`, browser-only externals stubbed) and runs the fixtures in `scripts/eval-fixtures.mjs` through the retrieval modes, reporting Hit@K/MRR per mode and per split (test = the pass/fail gate, train = tuning reference); exits non-zero only on held-out test-split misses. A pre-run gate validates split integrity (V1–V7) and the test-query corpus-hygiene rule and fails fast on violations. Flags: `--modes=bm25,vector,hybrid,decide` (default all), `--topk=5`. `bm25` is offline; `vector`/`hybrid` download the prompt-router checkpoint (~357 MB, cached in `~/.cache/huggingface`); `decide` downloads the GLiNER2.5-Decide checkpoint (~345 MB, q4f16, cached). Extend `eval-fixtures.mjs` when adding new sources or actions — tuning questions get `split: 'train'`, held-out evaluation questions get `split: 'test'` plus a `note` provenance marker (hand-authored only; test queries are immutable after the freeze).
- `npm run eval:chain` — retrieval, context-injection, and theme-action evaluation (`scripts/eval-chain.mjs`): runs the retrieval and action/context-injection steps (`retrieve()` → `decideAction` (heuristic theme actions, no LLM call syntax) or `buildContextText`) over every fixture × mode without loading or running the chat language model or answer judge, reports retrieval/injection/action metrics and average latency per mode × split, writes the committed artifact `src/data/evalResults.ts` (per-split aggregates, `gateSplit: 'test'`), and exits non-zero only on held-out test-split failures (runtime traces are test-side data and still gate the run). Reuses the shipped modules via `scripts/eval-lib.mjs` (transpile + browser stubs incl. disk-backed `useLlmsContent`); the browser never runs it. Flags: `--modes=bm25,vector,hybrid,decide` (default all), `--topk=5`, `--traces=<file|dir|url>` (repeatable). Fast iteration: `npm run eval:chain -- --modes=bm25`.
- Runtime traces: the **Save trace** button inside the showcase's "Technical details" disclosure (`src/composables/useTraceRecorder.ts`) downloads a finished session as STS-format JSONL (`harness: "about-me.mini-michi"`, opens in the HF trace viewer). Drop it into `frontend/traces/` (gitignored except its README) and the default eval scores it historically — re-runs retrieval to check the recorded injected sources are still in top-k or the recorded action is valid (`scripts/trace-lib.mjs`). `traces/*.jsonl` is never committed.
- Artifact: `src/data/evalResults.ts` is a **generated, committed** module (interface + data co-located) that the "Chat with my website" blog article renders (`src/components/BlogArticle.vue`, inlined on the single page). It is regenerated ONLY by `npm run eval:chain` — `prebuild` never runs the eval. A stale artifact is normal and visible (the section shows `generatedAt`).

## AI chat & content system (on-device)

The site is also an on-device AI demo. Mini-Michi runs a real SLM in the browser in the always-open inline showcase; the home-only floating launcher is a separate navigation helper that uses the same retriever but never loads the model. In the showcase, before each reply the retriever ranks the site's content sources, the top ones are injected into the context, and the model answers in a single pass; theme changes are applied directly by the retriever — the model never emits a tool call. Answers never move the page: each one links its injected sources as anchor links instead. Everything runs client-side — no backend, no API keys.

- Chat model: `LiquidAI/LFM2.5-350M-ONNX` via `@huggingface/transformers`, loaded lazily in `src/composables/useChatModel.ts` (q4 on WebGPU, q8 on WASM; WebGPU-first with a WASM q8 fallback — see the retrieval bullet), streamed token-by-token. Loaded on first send; disposed on Clear.
- Registry: `src/tools/registry.ts` — `SOURCE_DEFS` (granular content sources `about_bio`/`about_education`/`about_skills`/`about_hobbies`/`projects`/`contact`/`blog`/`blog:<slug>`/`site_index` + the `set_theme` action), retrieval helpers `getSourceDocs()`/`filterSources()`/`sourceChars()`, `getSourceContent()`/`buildContextText()` (fetch + char-budgeted injection, `MAX_INJECT_CHARS`), `buildSystemPrompt(contextText)`, and the deterministic `decideAction(query, rows, currentTheme)` (set_theme must rank first above `ACTION_MIN_SCORE`; explicit color wins, else the theme cycles). No tool-call parsing or executors.
- Retrieval (`src/composables/useToolRetrieval.ts`): before every reply the chat retrieves the top-k most relevant candidates and injects **only** those content sources into the context. Modes: `bm25` (pure BM25 over the alias-enriched source docs, instant, always available), `vector` (one pass of the zero-shot prompt-router checkpoint `kucukkanat/LFM2.5-Encoder-350M-Prompt-Router-ONNX`, q8, lazy ~357MB download: the query and all candidate names go into a single "Categories:\n- …\n\nText:\n…" prompt, with the trained cosine head (scale/bias from the model's `config.json`) and byte-level-BPE span pooling done in JS; WebGPU is attempted first with WASM fallback), `hybrid` (Reciprocal Rank Fusion of BM25 + vector-search scores), `decide` (GLiNER2.5-Decide decision classifier `onnx-community/GLiNER2.5-Decide-mobile-ONNX`, lazy ~345MB download, disposed on Clear: the query is the state, the `SOURCE_DEFS` names are the labels, `marker_positions` → softmax per source — the GLiNER2 processor is ported in-repo per `specs/003-gliner-decide-retrieval/contracts/decide-mode.md`). Decide loads **WASM q4f16 only** — the repo ships only the Q4 graph and ORT's WebGPU EP has no `GatherBlockQuantized` kernel, so a WebGPU attempt would always fail. transformers.js chains every browser session creation through a module-level promise (`webInitChain`, never reset after a rejection), so ONE failed session-creation call permanently breaks ALL further model loads (vector/decide/chat) for the page lifetime — vite HMR does not reset it, so a full page reload is required to recover. Loaders must therefore never fire a session creation that is guaranteed to fail (WebGPU-first for the router is safe because that graph runs on WebGPU; never re-enable WebGPU for decide) and every `loadVector()`/`loadDecide()` call site must `.catch()` so failures surface only in the panel error state. The webgpu/wasm verdict comes solely from `detectDevice()` (`src/composables/detectDevice.ts`), which mirrors ORT's actual init — `requestAdapter({ powerPreference: 'high-performance' })` (what transformers.js pins) plus a real `requestDevice()` — because a plain `requestAdapter()` can succeed on browsers (notably Firefox with WebGPU enabled, e.g. Linux/no-Vulkan stacks) whose ORT-shaped adapter/device calls then fail in-session; the fallback to WASM must therefore happen at detection time, never after a poisoned session attempt (the chat loader additionally catches a WebGPU attempt failure — only recoverable when no session was created yet, e.g. a failed q4 download). `vite.config.ts` aliases `onnxruntime-web/webgpu` → the full `ort.bundle.min.mjs` bundle because the webgpu-optimized bundle omits the int4 WASM kernel registrations (`GatherBlockQuantized`/`MatMulNBits`) that the DECIDE graph needs — the full bundle registers them AND keeps the WebGPU EP (vector/chat unchanged). The full bundle must also be paired with the **JSEP** wasm factory, so every loader must override `env.backends.onnx.wasm.wasmPaths` to the `ort-wasm-simd-threaded.jsep` files on jsdelivr via the shared `useJsepWasm()` (`src/composables/useJsepWasm.ts`, applied by the chat, router and decide loaders right after importing the transformers module — the module-level env is shared and only configurable while `wasmPaths` is still unset) — transformers.js otherwise points the browser at the non-JSEP/asyncify factory, which can't dispatch the int4 kernels. Vector search is never forced by the chat loop (the showcase only warms the loader via `loadVector`) and decide is never forced either (gated behind an explicit "Load DECIDE" action in the tool selector inside "Technical details" — selecting the DECIDE chip shows a download gate with a Load button instead of auto-starting the ~345MB fetch) — they fall back to bm25 unless already loaded or if a pass fails. The scorer's preprocessing is deliberately de-tuned: verbatim Lucene `_english_` + `_german_` stop sets and a standard letter/digit tokenizer — no fixture-derived stopwords, no alias boosting inside the scorer. The retriever loading bars are labeled and cancellable via `disposeVector()`/`disposeDecide()`. Tracked via shared `mode`/`topK`/`lastQuery`/`lastResult`/`vector`/`decide` refs.
- Visual panel: `src/components/ToolSelectorPanel.vue` (rendered inside the showcase's collapsed "Technical details" disclosure, never in the default view) shows ranked candidates, score bars, `IN CONTEXT` tags and a pruned-% stat; it shares `lastQuery`/`lastResult` with the chat. Launcher lookups call `retrieve(…, { record: false })` so they never overwrite that panel. The default transcript shows a plain **Sources** row of anchor links under each answer (built from the injected sources via `src/tools/sourceLinks.ts`) instead of per-turn retrieval rows, plus a compact `action` note for theme changes.
- Launcher (navigation helper): `src/composables/useChatNav.ts` + `src/components/NavSurface.vue` (inside the home-only `AssistantLauncher.vue` dialog titled "Find it on this page"). It ranks content sources with `retrieve()` (bm25, or vector/decide only if already loaded — it never forces a model download) and navigates to the best match through `navigateToAnchor()` in `useHashNavigation.ts` (scroll + spotlight + hash). Below the input it shows only the current query's ranked matches and a retriever stats line (candidates, top-k, effective mode/fallback, pruned %, latency) — never a conversation transcript or past queries; the ranking is cleared when the panel reopens. It stays open on wide screens and closes on ≤480 px so the unlocked page is visible. A `site_index` ("what can you do?") query lists the four bands and goes to the top of the page; no match stays put with a short notice. It does not touch the model state.
- Retrievable content: content sources map to `public/llms/*.md` via `src/composables/useLlmsContent.ts` (sections, projects, blog) and to `aboutMeMarkdown(topic)` from `src/data/siteData.ts` (the four about topics). `site_index` is generated from `listContentItems()`. Source labels and anchor destinations live in `src/tools/sourceLinks.ts` (used by both the inline source rows and the launcher); the inline chat has no page side-effects. The site is one page: the blog article (`BlogArticle.vue`) and the full project list live inline in their bands, and every band, card and blog entry is a deep link (`#education`, `#blog-<slug>`, `#projects`, …). `useHashNavigation.ts` keeps the URL in sync, powers the `SectionNav.vue` "Jump to" strip, and rewrites retired `#/...` URLs plus the old `#about-*` card ids onto the canonical anchors.
- The chat, vector and decide models are disposed on Clear to free memory (`dispose()` + `disposeVector()` + `disposeDecide()`).

### Adding a new always-open section (e.g. a new `SectionId`)

Sections are permanent, always-open bands — there is **no** visitor-facing collapse. Only the assistant hides/shows them. New sections touch many places — grep for the existing ids (`about`, `blog`, `projects`, `contact`) to find them all:
- `SectionId` union + `DEFAULT_SECTIONS` (visible only, no `expanded`) in `src/composables/useSiteLayout.ts`; use `showcaseVisible`/`setShowcaseVisible` for any non-`SectionId` band.
- Fixed composition order + `isVisible(id)` gating in `src/components/HomePage.vue` (the home page is not a data-driven loop).
- new section component in `src/components/` — copy the static `.pixel-window` skeleton from `ProjectsSection.vue`: `<section aria-labelledby="…">`, a `.pixel-window__bar--static` `<h2>`, always-rendered content, **no** `<button>` header, `aria-expanded`, `aria-controls`, chrome squares or `−`/`+`.
- a new content source in `SOURCE_DEFS` (`src/tools/registry.ts`) with `section` (+ `slug`/`topic`/`spotlight`), so the retriever can find and inject it
- an entry in `SectionNav.vue`'s "Jump to" strip, in page order (the strip is sticky above 640px and marks the band that fills the screen)
- `SECTION_LABEL` in `src/composables/useChatSession.ts`
- a new `public/llms/<id>.md` (add to `scripts/generate-llms-txt.mjs`), include it in `LLMS_FILES` in `src/composables/useLlmsContent.ts`, and link it in `llms.txt` — this makes it retrievable.
- add a fixture to `scripts/eval-fixtures.mjs` when adding a source or action.

## Statistics band (build-time derived)

`src/data/siteStats.ts` is the **only** producer of displayed statistic values. `buildStatGroups({ buildYear, site, eval, sources, maxInjectChars, defaultMode })` is pure: no `Date`, `window`, `fetch`, `localStorage` or network access. Values come from `src/data/siteData.ts`, the committed `src/data/evalResults.ts` artifact (test split only), `SOURCE_DEFS`/`MAX_INJECT_CHARS` in `src/tools/registry.ts`, and the Vite build year (`__BUILD_YEAR__`, `define` in `vite.config.ts`, declared in `env.d.ts`).

> The band itself is currently **not mounted** in `HomePage.vue` (it was dropped with the single-page layout). `StatsBand.vue`, `StatCard.vue` and `siteStats.ts` are retained and must stay correct; mount `<StatsBand />` back into the stack if the band should return.

- A statistic whose value cannot be derived returns `null` and is dropped before rendering — never render `0`, `—`, `n/a`, a skeleton or an estimate.
- A group with no statistics is not rendered; if every group is empty `StatsBand.vue` renders nothing at all (no wrapper, no gap).
- Only `numeric: true` cards count up (via `useCountUp`); labels, one-line notes, units and source links are the only authored fields.
- Changing `siteData`/`evalResults`/`registry` and rebuilding must change the card with no code edit — never hand-enter a number.

## Conventions

- Prettier: no semicolons, single quotes, printWidth 100 (`.prettierrc.json`). Eslint uses the prettier `skipFormatting` rule, so run `npm run format` to fix style.
- `@/` alias maps to `src/` (vite.config.ts, tsconfig.app.json).
- Components use `<script setup lang="ts">`. The site is styled as always-open "pixel-window" sections — reuse the existing `pixel-*` CSS naming in `src/assets/main.css`. No section is collapsible by a visitor: headings are static `<h2>`s, and only the assistant hides/shows bands.
- Motion goes through `src/composables/useReveal.ts` (`useReveal` for one-shot band reveals, `useCountUp` for numeric statistics). Do not add per-component observers or animation libraries; every animation must be disabled under `prefers-reduced-motion: reduce` and must never gate content visibility.
- The inline chat is one singleton (`src/composables/useChatSession.ts`, rendered only by `AiShowcase.vue`); never create a second chat conversation, message array or model instance, and technical detail belongs inside `ChatDetails.vue`. The launcher (`useChatNav.ts` → `NavSurface.vue`) is deliberately separate navigation state, not a chat: it renders no answers and shares no messages with the inline transcript.
- Node engine: `^20.19.0 || >=22.12.0`.

## Design guidelines (retro pixel-art CRT theme)

The look is retro pixel-art desktop meets CRT screen: a warm dark palette (near-black browns + amber/orange accents), chunky hard-edged UI with notched "pixel" corners and offset block shadows, a faint scanline overlay on the body, a blinking cursor after the name, and the display font `Bungee Spice` on the site name and section headings only. Everything should feel crisp, blocky, and slightly chunky — never glossy, rounded, or soft.

All styling lives globally in `src/assets/main.css` (components carry no `<style>` block); add new classes there with the existing `pixel-*` / `tech-*` / `project-*` naming (plus `model-*`, `tool-*` for the "How it works" cards, `stat-*` for the statistics band, `chat-*`/`assistant-launcher*` for the shared showcase, `blog-*`, `eval-*`).

- Use the CSS variables in `:root` (`--pixel-*` colors, `--shadow-hard`/`--shadow-soft`, `--font-display`/`--font-body`, `--type-*`) — never hardcode colors or fonts. Fonts are loaded via the Google Fonts import in `main.css`, no local assets.
- Aesthetic rules: warm dark palette, hard 2px+ offset shadows (`drop-shadow` or `--shadow-*`), pixel corners via `clip-path: polygon(...)` (4–8px notches), **no `border-radius` above 2px**, and stepped easing — use `steps(2, end)` transitions/animations, never smooth `ease`.
- Section chrome: each band is a `.pixel-window` with a static `.pixel-window__bar--static` heading row (`<h2>`, no toggle, no chrome squares, no marquee stripe) and always-rendered content. Per section: one 8px notched frame, one hard offset shadow, one heading row, at most one `.pixel-rule` divider and one accent family. The title bar ends with the band's mono path readout (`.pixel-window__crumb`, e.g. `~/blog`) on the right; the first band is a two-column introduction (status line, greeting, actions, framed portrait). The only disclosure controls in the site are the showcase's `<details>` "Technical details" and the assistant launcher — those are the only places `aria-expanded`/`aria-controls` legitimately appear.
- Reading rules: body copy and lists are capped at `max-width: 68ch` with `text-wrap: pretty`; nothing below `--type-micro` (0.75rem); `--font-display` is reserved for the name, section headings and the inline blog article title (kept at section-heading scale). Card titles, chat text and statistic numerals use `--font-body` with tabular numerals.
- Reuse building blocks instead of restyling: `.pixel-chip` (with `--amber`/`--orange`/`--red` variants), `.pixel-card`, `.pixel-list`, `.pixel-link`, `.pixel-link-btn`, `.pixel-contact__link`, `.stat-card`, `.chat-surface`.
- Respect the accessibility conventions already in place: `:focus-visible` outlines, `prefers-reduced-motion` handling, `text-wrap: pretty`, the `@media (max-width: 480px)` overrides, and the assistant launcher's Escape/focus-return behaviour.

## Deployment gotchas

- GitHub Pages workflow (`.github/workflows/gh-pages.yml`) deploys `frontend/dist` on push to `main`.
- `vite.config.ts` sets `base: '/about-me/'` — do not change it; the site lives at that path on GitHub Pages.
- `dist/` is gitignored — never commit build output.
- `public/mj.webp` (the avatar) is referenced as root-absolute `/mj.webp`; Vite rewrites it against `base` at build time.
